# Fresh Supabase Setup

This guide sets up UNI-TEL on a new Supabase project. The authoritative database source is:

`supabase/migrations/20260817000000_initial_schema.sql`

The old imported SQL snapshots were removed because this repository now targets a fresh project bootstrap, not migration continuity from a live database.

## 1. Create or link a Supabase project

Create a new Supabase project from the dashboard, then link the local repository:

```powershell
supabase login
supabase link --project-ref <your-project-ref>
```

The project ref is visible in the Supabase dashboard URL and API settings.

## 2. Configure local environment variables

Create `.env.local` in the repository root:

```env
VITE_SUPABASE_URL=https://<your-project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<your-anon-or-publishable-key>
```

Use the browser-safe anonymous/publishable key only. Do not put a service-role key in any `VITE_` variable.

## 3. Apply the database schema

Preferred CLI path:

```powershell
supabase db push
```

Manual dashboard path:

1. Open Supabase SQL Editor.
2. Paste the full contents of `supabase/migrations/20260817000000_initial_schema.sql`.
3. Run the script once against the empty project database.

Do not also run the deleted legacy migration files. They are intentionally no longer part of the project.

## 4. Deploy the import Edge Function

```powershell
supabase functions deploy import-academic-data
```

The function uses the Supabase service-role key from the Supabase Edge Function runtime environment. Do not expose that key in the Vite frontend.

## 5. Generate fresh TypeScript types after the project exists

The repository includes a manually aligned type contract so the app compiles before a live project exists. After applying the schema to your actual Supabase project, regenerate types:

```powershell
supabase gen types --lang typescript --linked --schema public > src/integrations/supabase/types.ts
```

Then run:

```powershell
npx tsc -p tsconfig.app.json --noEmit --pretty false
npm run build
```

If generated types differ, review the diff before committing.

## 6. Verify the database

Run these checks in Supabase SQL Editor after applying the schema.

### Required tables

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in (
    'profiles',
    'semesters',
    'subjects',
    'attendance_records',
    'marks_records',
    'notifications',
    'user_preferences'
  )
order by table_name;
```

Expected: seven rows.

### RLS enabled

```sql
select relname, relrowsecurity
from pg_class
where relnamespace = 'public'::regnamespace
  and relname in (
    'profiles',
    'semesters',
    'subjects',
    'attendance_records',
    'marks_records',
    'notifications',
    'user_preferences'
  )
order by relname;
```

Expected: every `relrowsecurity` value is `true`.

### Academic helper functions

```sql
select
  public.grade_to_points('A') as a_points,
  public.grade_to_points('A-') as a_minus_points,
  public.grade_to_points('F') as f_points,
  public.validate_grade_letter('NP') as non_gpa_status_supported,
  public.assessment_weightage_limit('Major Examination') as major_weightage_limit;
```

Expected:

- `a_points = 10`
- `a_minus_points = 9`
- `f_points = 0`
- `non_gpa_status_supported = true`
- `major_weightage_limit = 50`

### Generated calculation columns

After signing up one test user and inserting a semester, use authenticated app workflows to add attendance and marks. Then verify:

```sql
select subject_name, total_classes, attended_classes, percentage
from public.attendance_records
order by created_at desc
limit 5;

select subject_name, exam_type, total_marks, obtained_marks, weightage, percentage, weighted_percentage
from public.marks_records
order by created_at desc
limit 5;
```

Expected:

- attendance `percentage` is generated by the database
- marks `percentage` is `NULL` when `total_marks = 0`
- marks `weighted_percentage` is generated by the database

### Summary RPC

Run while authenticated through the app or via an authenticated SQL/API context:

```sql
select *
from public.get_user_academic_summary();
```

Expected: one row for the signed-in user after records exist, with SGPA/CGPA derived from subjects.

## 7. Local validation note

`supabase start` requires Docker Desktop to be running. If Docker is unavailable, do not claim local database reset validation. Use a disposable Supabase project and the SQL checks above.
